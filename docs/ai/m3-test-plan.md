# Test plan: M3 storage, updates, and recovery

- Acceptance/invariants: all six M3 automated criteria; fixed formats/layout; inactive-only staging; rejection before activation; interruption safety; trial rollback/confirmation; recovery repair; explicit data-only reset.
- Trust limits: 4096-byte manifest/request/record; 384-byte signature; slot-capacity payload; 32 KiB response headers; 15-minute update call; five redirects; 2048-byte resume metadata; 16 KiB child progress; 12–1024-byte credentials; at most two release keys.
- Host cases: GPT identity/capacity; every torn journal boundary; strict manifest and ring RSA-PSS; signer rotation/count; downgrade/corruption; redirect authority/userinfo/fragment/path; strong ETag and exact Content-Range; metadata mismatch; reread verification; terminal restoration model; secret redaction; API/status/update/health transitions.
- Fault cases: interruption during download/write/flush/reread/journal/reboot/health; short and oversized response; `200` restart; inconsistent `206`; engine failure; invalid LUKS bytes; both slot failures; malformed repair/reset grammar.
- Unsafe coverage: warnings-denied Clippy and focused termios/mlock/memfd/UEFI tests; Miri only for host-executable private boundaries where libc calls are mocked; each `cargo xtask check` runs a fixed-seed 1000-input libFuzzer smoke pass across journal, container-header, and manifest decoding.
- x86_64: native GitHub-hosted pinned-image `cargo xtask test --arch x86_64`; retain redacted per-scenario QEMU logs, selector/system/recovery/init/update/partition/variable-store hashes, and the uploaded unsigned-artifact digest. The matrix rejects unsigned and altered selector, normal-slot, and recovery EFI payloads, then exercises overlapping current/next db trust and old-db removal.
- aarch64: native GitHub-hosted pinned-image `cargo xtask test --arch aarch64`; retain the equivalent Secure Boot matrix, hashes, and unsigned-artifact digest, and note QEMU `virt` is not physical-device evidence.
- Update fixture: acceptance-only kernel/init/updater artifacts use virtio-net DHCP, an embedded disposable CA and fixed `https://10.0.2.2:8443` origin, and a process-local RSA-3072 release key. A strong-ETag OpenSSL HTTPS response installs sequence 1 to B; the same disk is restarted and must report `confirmed=b sequence=1` after the ten-second health gate.
- Signer: pinned `cargo xtask check` provisions a disposable SoftHSM token, generates a PKCS#11-sensitive RSA-3072 object through OpenSC, packages through libp11/OpenSSL with RSA-PSS/SHA-256, and independently verifies the exact manifest signature. M3 promotion separately requires an encrypted software token, backup restore, and hash-chained signing evidence; hardware non-exportability is an M11 gate.
- Environment: Rust 1.97.1 pinned image digest from `policy/build-image.lock`; disposable keys and local HTTPS fixture only; no production secrets. Timeout every child/QEMU run and retain redacted logs.
- Out of scope: owner ceremony, software-token backup/restore, environment/runner, and public-release gates cannot be automated or inferred from local tests; ADR 0002 permanently removes independent review and second-person witnessing. YubiHSM ceremony/audit/restore is deferred by ADR 0004 to M11. M4 hardware certification is not M3 evidence.
